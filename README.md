# Сервис отчётов по проектам разработки

Формирует по запросу проектного менеджера отчёт о текущем состоянии проекта на основе
данных главного сервиса «Разработки» (`http://ryzhov-as.neurosoft.ru:8501/portfolio`)
и хранит все отчёты в архиве: зафиксированный отчёт изменить и удалить нельзя, а черновик — можно.

## Запуск

Нужен только Python 3.12+ — внешних зависимостей нет. В папке сервиса лежат файлы для двойного клика:

| Файл | Что делает |
|---|---|
| `Запустить сервис.bat` | запускает сервис и открывает его в браузере; если он уже запущен — просто открывает. Окно не закрывать, пока сервис нужен |
| `Остановить сервис.bat` | после подтверждения останавливает сервис (процесс, слушающий порт 8600) |
| `Открыть сервис.url` | ярлык на http://localhost:8600/ |
| `Создать резервную копию.bat` | делает резервную копию базы и показывает список копий |
| `Восстановить из копии.bat` | показывает копии, спрашивает имя файла и подтверждение, восстанавливает базу (сервис должен быть остановлен) |

То же из командной строки:

```bash
python run.py
```

Интерфейс откроется на `http://<хост>:8600/`; коллеги открывают `http://<имя-ПК>.neurosoft.ru:8600/`.

| Переменная окружения | По умолчанию | Назначение |
|---|---|---|
| `MAIN_URL` | `http://ryzhov-as.neurosoft.ru:8501` | адрес главного сервиса |
| `MAIN_NO_PROXY` | `1` | ходить к главному сервису напрямую, минуя прокси |
| `REPORT_DB` | `data/reports.sqlite3` | файл архива отчётов |
| `REPORT_HOST` / `REPORT_PORT` | `0.0.0.0` / `8600` | адрес веб-сервера |
| `FIRST_REPORT_DAYS` | `30` | период первого отчёта по умолчанию (дней) |
| `BACKUP_DIR` | `data/backups` | папка резервных копий (лучше сетевая) |
| `BACKUP_INTERVAL_HOURS` | `24` | как часто делать копию автоматически (0 — выключить) |
| `BACKUP_KEEP` | `30` | сколько последних копий хранить |

Тесты: `python -m unittest`

## Обновление на другом ПК

Проект обновляется из GitHub файлом `Обновить проект.bat` (двойной клик):

1. Проверяет, что сервис остановлен (порт 8600), и что в папке нет ваших правок кода.
2. Забирает изменения из `origin/main` и показывает список новых коммитов.
3. Обновляет файлы. **Локальная база отчётов `data/reports.sqlite3` сохраняется и возвращается на место** —
   отчёты, созданные на этом ПК, при обновлении не теряются; новые резервные копии в `data/backups` тоже остаются.
4. Прогоняет тесты (`python -m unittest`) и печатает установленную версию.

Если сервис запущен, сначала закройте его: `Остановить сервис.bat`. Если в папке есть правки кода,
скрипт откажется обновляться, чтобы их не потерять: сохраните их (`git stash`) или отмените (`git restore .`).

Вручную то же самое (из папки проекта):

```bat
copy data\reports.sqlite3 %TEMP%\reports.sqlite3
git fetch origin
git reset --hard origin/main
copy %TEMP%\reports.sqlite3 data\reports.sqlite3
```

Новый ПК с нуля: `git clone https://github.com/Grenlays/project_report`, затем `Запустить сервис.bat`.
Обычный `git pull` в этой папке не подходит: база отчётов лежит в репозитории и на каждом ПК своя,
поэтому `pull` либо конфликтует, либо перезаписывает локальные отчёты.

## Связь с главным сервисом — только чтение

Вход — аккаунт наблюдателя (`POST /api/v1/auth/login-viewer`, без пароля).
Клиент (`report_service/main_client.py`) разрешает только GET-запросы и этот вход;
любой другой запрос он отклонит, не отправив. Используемые данные:

| Данные | Эндпоинт |
|---|---|
| Проект: название, направление, менеджер, статус, тип | `GET /portfolio/project-status` |
| Ключевые точки | `GET /portfolio/project-milestones` |
| Этапы (версии): срок, планируемые результаты, закрыт ли | `GET /portfolio/calendar-events` |
| История переносов срока этапа | `GET /portfolio/version-metadata/{id}/date-changes` |
| Трудозатраты сотрудников по этапам и неделям | `GET /portfolio/projects/{проект}?with_weekly=true` |
| Сотрудник → подразделение, цвета подразделений | `GET /portfolio/filters` |
| Срок завершения разработки (планируемая, желаемая дата, Дата МП) | `GET /roadmap` |

## Содержание отчёта

1. **Шапка**: название проекта, продуктовое направление, менеджер проекта, статус, тип, дата проведения отчёта, отчётный период.
2. **Сроки проекта** — три плитки, крупно показано время, мелко — дата:
   * сколько прошло с открытия проекта и с начала работ до даты отчёта (даты — из реестра проектов);
   * **«Срок завершения разработки»** — самая дальняя из трёх дат дорожной карты главного сервиса:
     «Планируемая дата» (`end_status_date` при статусе «плановая»), «Желаемая дата» (`end_status_date`
     при статусе «желаемая») и «Дата МП» (`mp_date`). Под сроком указано, какая это дата (если совпадают
     несколько — все). Крупно — сколько осталось до конца этого месяца или на сколько срок просрочен.
     Если проект разбит на части (J090, J090#2), по каждому виду берётся самая поздняя дата частей.
     Если дат нет — «не задан»; если разработка завершена — «разработка завершена» с датой.
     В отчётах, сформированных до этого изменения, сохранена только Дата МП — они показывают её.
3. **Ключевые точки** в две колонки: актуальные (срок — текущий месяц или позже) и закрытые с момента предыдущего отчёта (план → факт, отклонение в месяцах).
4. **Этапы, закрытые с момента предыдущего отчёта**: первоначальная → фактическая дата, отклонение в днях, трудозатраты и полученные результаты.
5. **Текущие этапы**: срок, признак просрочки, первоначальный срок с числом переносов, трудозатраты и планируемые результаты.
6. **Трудозатраты по проекту** (в конце отчёта): всего по проекту (с первой недели учёта в главном
   сервисе по дату отчёта) и за отчётный период — по всем этапам и списаниям вне этапов. Под каждой из
   двух цифр — свой раскрывающийся блок «По подразделениям»: часы и доля каждого подразделения
   (для периода — только подразделения, у которых были списания в периоде).
   Для отчётов, сформированных до появления раздела, часы считаются по данным главного сервиса
   за недели до даты отчёта (сам отчёт не меняется).

В обеих таблицах этапы сгруппированы по ответственному подразделению (группы по алфавиту,
этапы без подразделения — в конце); в строке группы — число этапов и сумма часов (всего и за период).
Разделы «Этапы, закрытые с предыдущего отчёта» и «Текущие этапы» целиком сворачиваются щелчком по их
заголовку (или оба сразу — ссылки «разделы: развернуть · свернуть»). Группу можно свернуть и развернуть щелчком по её строке (или все сразу — ссылки «группы: развернуть · свернуть»
над таблицами); свёрнутые группы запоминаются до закрытия вкладки, при печати выводятся все этапы.

Результаты этапа показываются крупным шрифтом с сохранением переносов строк, до 5 строк в таблице.
Если текст длиннее (такая ячейка подсвечивается при наведении), при наведении мыши всплывает окно
с полным текстом; при печати и в PDF текст выводится целиком.

Строка этапа раскрывается по клику: в ней полный текст результатов и трудозатраты по подразделениям
(всего и за период, цвета подразделений — как в главном сервисе). В свёрнутом виде показаны
общая сумма часов и часы за период.

**Трудозатраты.** «Всего» — все часы, списанные на этап. «За период» — часы за недели, которые
начинаются в день начала отчётного периода или позже: главный сервис хранит трудозатраты по неделям,
поэтому неделя, на которую пришёлся предыдущий отчёт, в новый период не входит. Сотрудники без
подразделения попадают в строку «Подразделение не указано».

### Как определяется «с момента предыдущего отчёта»

* Отчётный период начинается с даты проведения предыдущего отчёта по проекту.
  Для первого отчёта менеджер выбирает начало периода сам (по умолчанию 30 дней назад).
* В каждом отчёте сохраняется снимок исходных данных проекта. Следующий отчёт сравнивает
  с ним текущее состояние: в «закрытые» попадает то, что в прошлый раз было открыто, а теперь закрыто.
* **Ключевые точки.** В главном сервисе у точки только одна дата (месяц и год).
  Плановая дата — срок точки при её первом появлении в отчётах этого сервиса. Фактическая — срок
  в главном сервисе на дату отчёта. Точка считается пройденной, когда её месяц закончился.
* **Этапы.** Первоначальная дата — первая плановая дата из истории переносов главного сервиса;
  если истории нет — дата из первого отчёта. Фактическая дата — плановая дата этапа на момент закрытия.

## Хранение отчётов

* SQLite, таблица `reports`: дата и время проведения, период, автор, содержимое и снимок
  исходных данных, контрольная сумма SHA-256.
* Пока отчёт не зафиксирован, его данные можно пересобрать по актуальному состоянию главного сервиса,
  а сам отчёт — удалить. После фиксации версия неизменяема:
  * в интерфейсе и HTTP-API нет маршрутов правки содержимого зафиксированного отчёта;
  * на уровне БД триггеры запрещают `UPDATE` и `DELETE` зафиксированного отчёта;
  * при просмотре отчёт сверяется с контрольной суммой.
* Отчёт можно распечатать или сохранить в PDF, скачать отдельным HTML-файлом или выгрузить в JSON.

### Обновление данных и удаление черновика

Пока отчёт — черновик, над ним доступны две операции (обе с подтверждением в окне):

* **«⟳ Обновить данные»** (в панели над отчётом) — отчёт заново собирается по актуальным данным
  главного сервиса: статус и сроки проекта, ключевые точки, состав, сроки и результаты этапов,
  трудозатраты, срок завершения разработки, снимок для следующего отчёта.
  **Дата отчёта, отчётный период, автор и ссылка на предыдущий отчёт не меняются.**
  Примечания к этапам и сводным группам (вместе с изображениями), изменённый текст результатов
  и удалённые этапы сохраняются — они хранятся отдельно от содержимого отчёта.
  Если главный сервис недоступен, отчёт остаётся прежним, а в ответе — ошибка 502.
* **«✕ удалить»** в архиве отчётов — удаляет черновик вместе с примечаниями, изображениями и правками
  этапов, спрашивая подтверждение с предупреждением о необратимости. Зафиксированный отчёт удалить
  нельзя: в архиве у него нет кнопки, а запрос отклоняется (409). Восстановить удалённый отчёт можно
  только из резервной копии базы.

Ссылка «предыдущий отчёт» на карточке отчёта показывается только если тот отчёт ещё существует.

### Корректировка этапов и фиксация отчёта

Пока отчёт не зафиксирован, менеджер может его скорректировать — поверх сохранённых данных,
сами данные из главного сервиса при этом не меняются:

* **Результаты этапа** — кнопка «✎ изменить» в столбце результатов («Полученные результаты» у закрытых
  этапов, «Планируемые результаты» у текущих). Изменённый текст помечается «изменено»; исходный текст из
  главного сервиса виден в окне правки и в раскрытой строке этапа, кнопка «Вернуть исходный» отменяет правку.
* **Удаление этапа из отчёта** — «✕ удалить этап» под названием, с подтверждением. Удалённые этапы
  перечислены под таблицей, до фиксации их можно «вернуть».
* **Примечания** — см. ниже.

Кнопка **«🔒 Зафиксировать отчёт»** (справа над отчётом) открывает окно с предупреждением, что версию
изменить больше будет нельзя, и спрашивает, кто фиксирует. После фиксации:

* появляется уведомление «Отчёт зафиксирован — версию изменить больше будет нельзя»;
* в шапке отчёта — «🔒 Зафиксирован <дата> · <кто>», в архиве и истории проекта — «зафиксирован»
  (незафиксированные — «черновик»);
* кнопки правки исчезают, сервер отвечает на любые правки ошибкой 409, а триггеры БД запрещают изменять
  правки, примечания, изображения и саму фиксацию — отменить её нельзя;
* в момент фиксации сохраняется контрольная сумма правок и примечаний; при просмотре она проверяется
  вместе с контрольной суммой отчёта.

Правки хранятся в таблице `stage_edits`, фиксация — в `report_locks`; в JSON отчёта они идут полями
`stage_edits` и `lock`.

### Примечания к этапам и к сводным группам

* В обеих таблицах этапов есть столбец «Примечание». Кнопка «+ добавить» / «✎ изменить» открывает
  окно: текст и изображения (PNG, JPEG, GIF, WebP до 10 МБ — файлом, перетаскиванием или Ctrl+V).
* Такой же столбец есть у строк-итогов по подразделению («ОРПО · 1 этап» и т. п.): примечание ставится
  на всю сводную группу — по тегу подразделения. Группы «текущих» и «закрытых» этапов — разные
  примечания. В JSON такие ключи выглядят как `grp:<раздел>:<подразделение>`.
* Примечания — редактируемый слой поверх отчёта: их можно менять и удалять до фиксации отчёта.
  Хранятся в таблицах `stage_notes` и `note_images`, в содержимое и контрольную сумму отчёта не входят.
* В скачанном HTML примечания показываются без редактора, изображения встроены в файл;
  в JSON отчёта они идут отдельным полем `stage_notes`.
* Лимиты настраиваются переменными `NOTE_IMAGE_MAX_MB` (по умолчанию 10) и `NOTE_TEXT_MAX` (20000 символов).

## Резервные копии

В копию попадает вся база: отчёты, правки этапов, фиксации, примечания и изображения.

* **Автоматически.** Пока работает сервис, копия делается раз в `BACKUP_INTERVAL_HOURS` часов
  (по умолчанию 24) и сразу при запуске, если последней копии больше этого срока.
* **Вручную.** Кнопка «Создать копию сейчас» внизу страницы «Архив отчётов» (там же видно, когда
  была последняя копия и не устарела ли она) или из командной строки: `python backup.py`.
* **Где лежат.** `data\backups\reports_ГГГГММДД_ЧЧММСС.sqlite3`. Хранятся последние `BACKUP_KEEP`
  копий (по умолчанию 30), старые удаляются автоматически. Папку можно сменить переменной
  `BACKUP_DIR` — лучше указать сетевую папку на другом компьютере, иначе при выходе из строя
  этого ПК пропадут и база, и копии.
* **Надёжность.** Копия делается штатным механизмом SQLite (корректно во время работы сервиса),
  проверяется `PRAGMA integrity_check` и только после этого появляется в папке.
* **Список копий:** `python backup.py list`.
* **Восстановление:** остановите сервис, затем `python backup.py restore reports_20261116_155339.sqlite3`
  (имя файла из папки копий или полный путь). Текущая база перед восстановлением сохраняется в
  `before_restore_….sqlite3` — такие файлы ротацией не удаляются. Пока сервис запущен, восстановление
  не выполнится.

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | список проектов (фильтр по менеджеру, `?all=1` — включая завершённые) |
| GET | `/projects/<код>` | карточка проекта, кнопка формирования отчёта, история отчётов |
| POST | `/projects/<код>/reports` | сформировать и сохранить отчёт |
| GET | `/reports` | архив всех отчётов (`?project=J028` — только по одному проекту) |
| GET | `/reports/<id>` | просмотр отчёта |
| GET | `/reports/<id>/download` | отчёт отдельным HTML-файлом |
| GET | `/reports/<id>.json` | отчёт в JSON (с примечаниями в `stage_notes`) |
| POST | `/reports/<id>/refresh` | обновить данные черновика из главного сервиса |
| POST | `/reports/<id>/delete` | удалить черновик вместе с примечаниями и правками |
| POST | `/reports/<id>/notes/<этап или группа>` | текст примечания (JSON `{"text": ...}`) |
| POST | `/reports/<id>/notes/<этап>/images` | добавить изображение (тело — файл) |
| POST | `/reports/<id>/notes/<этап>/images/<img>/delete` | удалить изображение |
| GET | `/notes/images/<img>` | изображение из примечания |
| POST | `/reports/<id>/stages/<этап>/description` | свой текст результатов (JSON `{"text": ...}`, `null` — исходный) |
| POST | `/reports/<id>/stages/<этап>/remove` | убрать этап из отчёта |
| POST | `/reports/<id>/stages/<этап>/restore` | вернуть этап |
| POST | `/reports/<id>/lock` | зафиксировать отчёт (форма: `locked_by`) |
| POST | `/backups` | создать резервную копию сейчас |
